# 承认自己会死

引擎必须假设自己会失败。失败路径写了，才能在失败里体面地停下。

## 四仓的失败长什么样

`Hazel` 里没有失败隔离。`Application::Run` 每帧走层栈，`Renderer::Init` 在构造里抛异常，抛了全进程停：

```cpp
// Hazel —— 渲染初始化失败抛异常，全进程停
Application::Application() {
    Renderer::Init(); // 抛了就全停，没人接
    m_Window = Window::Create(...);
}
```

优点：短。缺点：抛了全停，没上报。生产里这就是崩溃 dump。

`MonoGame` 在 `Game.Run` 里包着 `try`，失败进顶层：

```csharp
// MonoGame —— 失败进顶层
try { Run(); } catch (Exception ex) { Log.Error(ex); } // 报人话
```

优点：新进程能拿到异常。缺点：顶层抓多了乱，只记日志不丢帧，失败记得没分级。

`Stride` 在 `GameBase` 里走 `GameStarted` 事件，初始化失败进系统分发：

```csharp
// Stride —— 初始化失败进系统分发
public static event EventHandler GameStarted; // 失败也走系统
```

缺点：系统多，失败定位要踩十道板。

`prisma-rev` 独占上下文，渲染线程死了主线程先查：

```rust ref="prisma:crates/prism-app/src/app.rs#L810-L827"
// 每帧自检：渲染线程死了就返回错误，不继续自旋
fn tick_frame() {
    if handle.is_finished() {
        return Some(shared.take_render_failure().unwrap_or("render thread exited".into()));
    }
    tick_sim(true); // 然后跑一圈逻辑和提取
}
```

失败原因落在仓库里，写入一次取走一次：

```rust ref="prisma:crates/prism-app/src/render_shared.rs#L334-L344"
// 失败原因落在仓库里：写入一次，取走一次
pub fn set_render_failure(&self, message: String) {
    *self.render_failure.lock().unwrap() = Some(message);
}
```

`horizon` 作需求方：失败分级要写清，事件走返回值，不靠异常飞。

## 四仓对照表

| 写法 | 上报 | 隔离 | 分级 | 适合谁 |
|---|---|---|---|---|
| `Hazel` 抛异常 | 不上报，全停 | 差，同进程连坐 | 差 | 先看一眼 |
| `MonoGame` 顶层捕获 | 上报，记日志 | 中，顶层接 | 中，分级少 | 传统生产图 |
| `Stride` 系统分发 | 上报，走系统 | 中，系统间 | 中，系统多 | 生态大，作架构对照 |
| `prisma-rev` 独立线程查 | 上报，带原因返回 | 好，渲染线程独立 | 好，能恢复的继续 | 本教程主线 |
| `horizon` 需求对齐 | 按事件分级 | 中 | 好，事件走返回值 | 需求方 |

表上能看：`Hazel` 短但全停，`MonoGame` 中但可上报，`Stride` 全但重，`prisma-rev` 隔离且分级。生产级写法定 `prisma-rev` 的组合。

## 本课定谁

不是选最简单，选生产级。单人引擎的生产级失败写法，我定 `prisma-rev` 的组合：渲染线程独立拥有上下文，主线程每帧自检，原因带回去，能恢复的继续。

理由有三条。

一是失败隔离。渲染线程崩了，主线程先查再报，不空转。`Hazel` 那种抛了全停的写法，线上必现白屏加高占用。

二是结构清楚。线程名字、设备名字、技术栈都在失败消息里。查日志能对上。

三是可测试。渲染线程挂掉、设备丢了、显存爆了，这三条生产路径在代码里都有名。教学代码只写快乐路径，生产代码先写这条。

```rust
// 本课定案：失败的样子
struct Fail {
    thread: String, // 哪个线程死了
    reason: String, // 为什么死
    fatal: bool, // 能不能恢复
}
```

## 手写最小示例

```rust
// 先报：把原因带回去
fn tick_frame() -> Option<String> {
    if handle.is_finished() {
        return Some(failure); // 把原因带回去
    }
    None // 没坏就报没坏，调用方继续跑
}
```

```rust
// 先报，再停：调用方拿着原因关窗口
if let Some(msg) = tick_frame() {
    log::error!("渲染失败：{msg}"); // 报人话
    exit(); // 走自己的出口
}
```

## 双语对照

C++ 里设备丢失走错误码：

```cpp
// C++ —— 设备丢失走错误码
VkResult r = device.waitIdle();
if (r == VK_ERROR_DEVICE_LOST) {
    log_error("显卡驱动重置，设备已丢失"); // 报人话
    shutdown(); // 走自己的出口
}
```

```bash
g++ main.cpp -o engine && ./engine
```

C# 里失败抛到顶层：

```csharp
// C# —— 渲染失败抛到顶层
try { Renderer.Draw(); } catch (Exception ex) {
    Log.Error("渲染失败：" + ex.Message); // 报人话
    Exit(); // 走自己的出口
}
```

```bash
dotnet run
```

三边一样：先报，再停。报要带上下文，停要有出口。

## 不该报的别报

能恢复的错误记一条继续跑，不能恢复的停下并报原因。报的时候把上下文带上：哪个线程、哪个设备、哪个文件。上下文在这一课是线程名字和设备名字。

:::tip{title="为什么这算生产级"}
生产代码为失败路径写了处理。教学代码只写快乐路径，生产代码要处理线程退出、设备丢失、显存不足这类少见但必然的路径。
:::

## 跟着看的结果

这一课验收：你能说出渲染线程死法就是一条失败路径怎么报、怎么停。

:::exercise{title="动手：故意让失败露面"}
故意让渲染线程提前退出，看主线程的检查能不能把原因打出来。把那行输出抄下来。再看日志里带没带上下文，线程名字、设备名字都在不在。
:::

## 四仓在同一页上

`Hazel` 的 `Renderer::Init` 抛了全停。`MonoGame` 的顶层捕获记日志。`Stride` 的系统分发走事件。`prisma-rev` 的渲染线程独立查它死了没。本课往下走，只跟第四种。
