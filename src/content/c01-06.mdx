# 一张课程地图

课程一共五十多章。这张图只管位置：现在在哪里，下一章去哪，跳过一章会缺什么。

## 六段顺序

第一段地基是底。造引擎、搭骨架、学借用检查、管时间、写主循环、处理失败、定配置、看诊断、保可复现。后段都长在上面，跳过地基去写渲染，等于没有时钟也没有主循环。

```diagram map
第一部 地基: 造一台发动机, 项目骨架, 借用检查的形状, 时间, 主循环, 失败, 配置, 诊断, 可复现
第二部 平台: 窗口, 事件, 输入, 显示器, 生命周期, 线程, 文件
第三部 渲染器: 图形接口选型, 实例与适配器, 设备与队列, 交换链, 第一帧, 缓冲区与顶点, 着色器, 管线
第四部 渲染架构: 帧图, 资源与句柄, 同步, 阴影, 后处理, 合批与剔除, 显卡数据流, 性能
第五部 世界: 实体组件系统, 查询与调度, 场景, 变换, 资源管线, 序列化, 动画, 物理
第六部 外壳: 编辑器, 热重载, 平台, 发布, 遥测, 协作
第七部 收束: 回顾引擎的形状, 下一台引擎
```

第二段平台是接缝。窗口、事件、输入、显示器、生命周期、线程、文件。引擎与操作系统的每一处接缝都在这里显式处理。

第三段渲染器是眼睛。从显存里画出三角形开始：选图形后端、实例适配器、设备队列、交换链、第一帧、缓冲区顶点、着色器、管线、摄像机、深度裁剪、纹理、材质光照、调试渲染。

第四段渲染架构是账房。能画一个东西之后，开始算一百个东西怎么画：帧图、资源句柄、同步、阴影、后处理、合批剔除、显卡数据流、性能。

第五段世界是房间。渲染器只是眼睛。现在给它一个世界：实体组件系统、查询调度、场景、变换、资源管线、序列化、动画、物理。

第六段外壳是门。引擎之外的引擎：编辑器、热重载、平台差异、发布、遥测、协作。最后收束：回顾引擎的形状，谈下一台引擎。

## 四仓的包地图

`Hazel` 的包地图在仓库根：`Hazel` 是引擎，`Sandbox` 是样例，`Hazelnut` 是编辑器。查一个东西先看根目录有哪个包。

```bash
# Hazel 的包先分：引擎、样例、编辑器，查一个从引擎点名
ls | head # 看引擎在哪个包
grep -rn "class Application" Hazel/src/Hazel/Core/Application.h | head # 看引擎主循环在哪
```

`MonoGame` 的包地图在框架仓根：`MonoGame.Framework` 是框架本体，`Tests` 是测试。查一个东西先看框架在哪个包。

```bash
# MonoGame 的包先分：框架、内容流水线、测试，查一个从框架点名
ls MonoGame.Framework | head # 看框架在哪个包
grep -rn "class Game" MonoGame.Framework/Game.cs | head # 看游戏入口在哪
```

`Stride` 的包地图在 `sources/engine` 下：`Stride.Engine` 是引擎，`Stride.Graphics` 是图形，`Stride.Games` 是游戏抽象。查一个东西先看引擎在哪个包。

```bash
# Stride 的包先分：引擎、图形、游戏，查一个从游戏抽象点名
ls sources/engine/Stride.Engine | head # 看游戏在哪个包
grep -rn "class Game" sources/engine/Stride.Engine/Engine/Game.cs | head # 看游戏入口在哪
```

图上一读就知道哪块是引擎，哪块是样例，哪块是编辑器。查东西先看地图，再下包。

## horizon 与 prisma-rev 在图里的位置

`horizon` 是 Java 版 Minecraft 26.3 的重写。它的世界生成、实体、红石、命令、数据包分在几个包里，游戏侧是 `horizon-client` 的 `game.rs`。教程里看到的时钟、tick、帧图都在它那边有真身。

`prisma-rev` 是从零写的渲染器。它按层分包：`prism-ecs` 是实体组件系统核心，`prism-gfx` 是跨场景的纯数据枚举，`prism-render` 是渲染后端，`prism-app` 是窗口和事件，`prism-platform` 是窗口后端。教程里看到的窗口、设备、交换链、帧图都在它那边有真身。

两边对着看，就知道哪层是标准，哪层是自研。`horizon` 的形状由原版规格拍板，`prisma-rev` 的形状由自己拍板。

## 章与课怎么对

课在 `src/content/curriculum.ts` 里只有标题。标题定下来，编号、文件名、静态页都自动跟着走。改课程表，导航自己更新。

```typescript
// 课程表只写标题，编号由代码推导——增删一课不让编号乱
export type Status = 'ready' | 'writing' | 'planned';
type LessonSpec = string | [title: string, status: Status];
```

状态分三种：已写完、正在写、只有标题。章的状态由课汇总。想知道现在写到哪，看课程表里哪个是已写完就知道。

手写最小示例在正文里。引用块只管跳转，下面手写的是精简教学版：

```rust ref="prisma:crates/prism-ecs/src/lib.rs#L495-L499"
// 组件池最小骨架：稠密数组 + 稀疏索引
struct ComponentPool<T> {
    dense: Vec<T>,             // 所有 T 紧凑存放，顺序访问快
    dense_entities: Vec<u32>,  // dense[i] 对应哪个 Entity
    sparse: Vec<u32>,          // sparse[entity] -> dense 下标，缺失为 u32::MAX
}
```

引用块只提供仓库、文件、行号和「固定 / 最新 / 历史」跳转，完整实现点引用块去 GitHub 看。教程代码行号从 1 开始，与真实文件行号无关。

## 双语对照

C++ 教程通常先学语言再学图形。C# 教程通常先学界面再学引擎。Rust 这条线把地基放第一段，后面都长在上面。同样的顺序在两边都有：地基不牢，渲染写一半就散。

:::tip{title="为什么分段"}
分段是怕后面没地基。地基在第一段定下来，后段只管一层。跳一层，下层就断。
:::

## 本课定谁

不是选最简单，选生产级。单人引擎的包地图，我定 `prisma-rev` 的层地图：工作区根固定成员，层之间不反向依赖。

理由有三条。

一是生产级。成员和依赖写死在清单里，环直接拦住。`Hazel` 那种全在根上，改个包名就断一片。

二是结构清楚。应用层管窗口，引擎层管运行时，渲染层管后端。查东西从应用层点名，名对得上。

三是可测试。层清楚了，测试也清楚。测试灌的都是包上层，不用把仓库全拖进来。
