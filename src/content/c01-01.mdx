# 造一台发动机

本书默认你没写过其他项目，也没装过 Rust。第 2 章已经装好工具链，这一课假设你能 `cargo run` 并看住输出。

## 先定评价标准

本课不按“最简单好写”选。按工业生产级选，维度只有五个：确定性、失败隔离、调度层级、线程归属、可测试性。`horizon` 仓由于不是实体组件系统架构，只作功能需求方参考：它告诉你引擎要做什么，不告诉你数据怎么摆。本课架构选型只看四仓里的实体组件系统式实现。

> 确定性：同样的输入能不能得同样的输出。失败隔离：一个线程崩能不能带倒整个进程。调度层级：步进、更新、后期各管哪一段。线程归属：谁拥有渲染上下文。测试：能不能喂固定时长看步进数。

## 四仓的最小一圈

`Hazel` 的主循环在 `Application::Run` 里：

```cpp
// Hazel —— 可变步进，一帧走一遍层
void Application::Run()
{
    while (m_Running) // 直到关闭
    {
        float time = Time::GetTime();
        Timestep timestep = time - m_LastFrameTime; // 两帧间隔
        m_LastFrameTime = time;
        for (Layer* layer : m_LayerStack) layer->OnUpdate(timestep); // 可变步进直接灌进逻辑
    }
}
```

### 优点

短，一眼看完。层栈加上几层只多几行。教学和启动最快。

### 缺点

步进跟着帧走，换 60 赫兹和 144 赫兹速度差一倍。没有上限和丢弃，长掉帧直接进“死亡螺旋”。同线程跑渲染和逻辑，崩了全停。按生产标准，这是教学品，不是线上品。

复现很简单：在 60 赫兹上速度刚好，换 144 赫兹快一倍，给一帧加 40 毫秒直接穿墙。

```bash
# 复现 Hazel 毛病：同一份代码换刷新率看速度
g++ main.cpp -o sandbox && ./sandbox # 60 赫兹记速度
# 换 144 赫兹再跑一次，看速度涨没涨
```

`horizon` 是功能需求方。它的时钟在 `horizon-client` 的 `clock.rs` 里：

```rust ref="horizon:crates/horizon-client/src/clock.rs#L393-L413"
// 累加真实时间，切出固定 tick；每帧上限 10，超出丢弃
let ticks = timer.advance_game_time(now_ms, |d| d.max(mspt));
// “刹车片”：每帧最多补 10 个 tick，超出的时长直接丢弃
ticks.clamp(0, 10) // 完整实现点引用块去看，这行是关键
```

它告诉你生产为何要速率管理、冻结、暂停和上限：服务器节拍是事儿，客户端画面是另事儿。它的架构不是实体组件系统，数据拼法不在本教程学范围内。

`MonoGame` 在 `Game` 里把固定步长写死， accumulator 攒满切一格，太长的一帧直接截掉：

```csharp
// MonoGame —— 固定步长写死，太长截掉
// _isFixedTimeStep = true; _targetElapsedTime = 1/60; _maxElapsedTime = 500ms
// 攒够一格就 DoUpdate 一次，超出一截就丢
```

打分上看，它比 `Hazel` 像生产品：步长写死，截断上限明码标价。缺点是代码是旧的 XNA 风格，组件按 `UpdateOrder` 排序，不算实体组件系统式解，线程还绑主线程。

`Stride` 在 `GameBase` 里走组件系统：`Game` 继承 `GameBase`，组件按顺序注册，`GameTime` 给步长。片段看它的接口：

```csharp
// Stride —— 组件系统：Game继承GameBase，组件按顺序注册
public class Game : GameBase, ISceneRendererContext, IGameSettingsService
```

缺点是工程量很大，读懂要几步起，且是 C# 生态里讨论最多的那款。教程用它作架构对照，不用它作主线：语言不对、版本负担高。

`prisma-rev` 在 `tick_sim` 里走整数纳秒累加器，追赶带上限：

```rust ref="prisma:crates/prism-app/src/app.rs#L1124-L1174"
// 单步模拟与提取提交：整数纳秒时钟，追赶带上限，完整实现点引用块去看
// 先测时间，再加累加器；输入事件不决定模拟速度
let now = Instant::now(); // 瞬间：现在
let elapsed = last_frame.map(|p| now.saturating_duration_since(p)).unwrap_or(Duration::ZERO);
const FIXED_STEP: Duration = Duration::from_nanos(16_666_667);
let mut fixed_steps = 0;
while self.fixed_accumulator >= FIXED_STEP && fixed_steps < 8 {
    engine.fixed_update(FIXED_STEP.as_secs_f32(), &self.input); // 跑一步
    self.fixed_accumulator -= FIXED_STEP; // 用掉一格
    fixed_steps += 1;
}
```

主循环失败隔离长这样：

```rust ref="prisma:crates/prism-app/src/app.rs#L810-L830"
// 每帧自检：渲染线程死了就返回错误，不继续自旋
fn tick_frame() {
    if handle.is_finished() {
        return Some(failure); // 把失败原因带回去
    }
    tick_sim(true); // 然后跑一圈逻辑和提取
}
```

逻辑本身分固定步和可变步两段，矩阵传播在调度末尾：

```rust ref="prisma:crates/prism-engine/src/engine.rs#L429-L472"
// prisma 逻辑：更新跑调度，末尾传播世界矩阵
pub fn update(&mut self, dt: f32, input_manager: &InputManager) {
    self.schedule.run(&mut self.world, dt); // 用户与 built-in 系统
    crate::scene::systems::hierarchy::hierarchy_system(&mut self.world); // 矩阵传播
}
```

## 四仓对照表

| 写法 | 确定性 | 失败隔离 | 调度层级 | 线程归属 | 测试 | 结论 |
|---|---|---|---|---|---|---|
| `Hazel` 可变步进 | 差，跟着帧走 | 差，同线程连坐 | 差，全在更新一处 | 差，没写死 | 差 | 教学品，作反例 |
| `horizon` 虚拟时钟 | 好，速率管理器 | 中，不崩 | 好，冻结暂停清 | 中 | 好，喂毫秒 | 需求方，作功能对齐 |
| `MonoGame` 固定步长 | 好，步长写死 | 中，截断后免转 | 中，组件排序 | 差，绑主线程 | 好 | 传统生产图，作步长对照 |
| `Stride` 组件系统 | 好，组件分工 | 中，系统多 | 好，排序可控 | 中，层数多 | 中 | 生态大，作架构对照 |
| `prisma-rev` 固定累加器 | 好，输入不决定模拟速度 | 好，渲染线程独立 | 好，三段分工 | 好，渲染线程拥有 | 好，喂纳秒 | 本教程主线 |

表上能看：`Hazel` 短但跑到线上就飘，`horizon` 牢但绑定原版规格，`prisma-rev` 既把步进写死、又把线程归属写死。`MonoGame` 和 `Stride` 帮你看清“生产”两个字的代价。

## 本课定谁

不是选最简单，选生产级。单人引擎的生产级写法，我定 `prisma-rev` 的组合：整数纳秒时钟、固定步长、每帧上限、渲染线程独立拥有上下文、固定步与更新分工、矩阵末尾传播。

理由有四条，都对应评价标准。

一是确定性。固定步长加上“输入不决定模拟速度”，重放才能对上。`Hazel` 那种两帧间隔灌进逻辑的写法，重放第一步就飘了。

二是失败隔离。上下文归渲染线程，主线程查它死了没。死了报原因退，不死继续跑。教学代码只写快乐路径，生产代码先写这条。

三是调度层级。固定步管物理，更新管逻辑，后期管画面。各一段，错了能定位到段。`Hazel` 全在 `OnUpdate` 一处，定位只能猜。

四是线程归属。谁拥有谁写死，ownership 清了，锁和通道才有意义。归属没写死的引擎，后面改交换链先崩。

```rust
// 本课定案：工业级时钟的样子
struct Clock {
    bank: Duration, // 累加器：攒着的余数
    step: Duration, // 步长：固定大小
    max_steps: u32, // 上限：每帧最多跑几步
}
```

三行就是全部家当。后面几课都从这三行长出去。

## 手写最小示例

```rust
// 手写最小：真实时间往累加器加时长，固定步长产出 tick
let mut bank: Duration = Duration::ZERO; // 攒着的余数
bank += elapsed; // 本帧进来多少，先加进去
while bank >= STEP {
    world::step(STEP); // 切一格出来干活
    bank -= STEP; // 用掉一格，剩下的是余数
}
```

```rust
// 刹车片：每帧最多补 8 个，超出的时长直接丢弃
let ticks = bank / STEP;
let ticks = ticks.clamp(0, 8); // 上限在看得见的地方
```

上面两段是教程主线。完整实现点引用块去看，行号不跟着变。

## 双语对照

C++ 里 `Hazel` 式的可变步进最常见，换成固定步长就多三行：

```cpp
// C++ —— 从 Hazel 的可变步进换成固定步长
void tick(float frame_dt) {
    accumulator += frame_dt; // 真实时间往累加器加
    while (accumulator >= STEP) {
        physics::step(STEP); // 固定步长干活
        accumulator -= STEP;
    }
    renderer::draw(alpha); // 画面拿余数插值
}
```

```bash
g++ main.cpp -o engine && ./engine
```

C# 里 `MonoGame` 式固定步长两行就是：

```csharp
// C# —— MonoGame 式固定步长：攒、切、上限
void Tick() {
    accumulator += Time.deltaTime;
    while (accumulator >= Step) {
        Physics.Step(Step);
        accumulator -= Step;
    }
}
```

```bash
dotnet run
```

三边步长都写死。写死才不会随刷新率飘。`horizon` 多了速率管理和暂停冻结，`prisma-rev` 多了线程隔离和矩阵传播。初学先拿固定累加器站住，后面再补那两件。

## 跟着看的结果

这一课验收只有一个：你能说出为什么教程选了 `prisma-rev` 的写法，不选 `Hazel` 的可变步进，也不先啃 `horizon` 的虚拟时钟，并说出 `MonoGame`、`Stride` 各差哪儿。

验收单只有四行，照着念就行：

```text
1. 逻辑只认固定步长，不认两帧间隔。
2. 累加器攒真实时间，攒够一格切一格。
3. 每帧上限看得见，超量时间直接丢。
4. 画之前先算，顺序定死。
```

四行对上了，这一课算过。下一课是三只时钟。
