# 为什么不能直接用增量时间

这一课只讲一个毛病：拿两帧的间隔时间去更新逻辑，刷新率一变行为跟着变。

## 毛病长这样

增量时间是上一帧到这一帧隔了多久。它随着显示器的节奏飘。60 赫兹下刚好，144 赫兹变快，掉帧时逻辑被拉长，角色穿墙。

```rust
// 错法：拿两帧间隔直接更新逻辑，刷新率一变行为跟着变
let dt = frame_end - frame_start; // 两帧间隔，抖动大
world::step(dt); // 用显示帧的抖动去驱动逻辑
```

这段在两仓里都不这么写。下面是真实做法，放在下一课。先记住毛病，别把毛病当成写法。

## 双语对照

C++ 里常见同样毛病：

```cpp
// C++ —— 同样的生产级毛病：两帧间隔驱动物理
auto now = std::chrono::steady_clock::now();
float dt = std::chrono::duration<float>(now - last).count();
physics::step(dt); // 144 赫兹下快一倍
```

C# 里也一样：

```csharp
// C# —— 同样的毛病：两帧间隔驱动逻辑
var dt = Time.deltaTime; // 两帧间隔
physics.Step(dt); // 刷新率一变就飘
```

两边都把显示抖动带进了逻辑。解法都是先把步进固定，再让增量只负责往累加器加时长。

## 跟着看的结果

本课验收只有一个：你能复述增量时间飘在哪。

:::exercise{title="动手：开对照实验"}
在演示里把刷新率从 60 改成 144，看移动速度涨没涨。涨了，你就亲手撞上了这个毛病。改回来。
:::
