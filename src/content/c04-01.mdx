# 为什么不能直接用增量时间

本书默认你没写过其他项目，也没装过锈语。第 2 章已经装好工具链，这一课假设你能 `cargo run` 并看住输出。

## 毛病先长这样

增量时间是两帧之间隔了多久。引擎里最常见的错法，是拿这个间隔去推物理和逻辑。

```rust
// 错法：拿两帧间隔直接更新逻辑，刷新率一变行为跟着变
let dt = frame_end - frame_start; // 两帧间隔，抖动大
world::step(dt); // 用显示帧的抖动去驱动逻辑
```

这段看着像数学，其实把显示器的节奏带进了逻辑。两仓里都不这么写。

## 三档刷新率下会发生什么

| 显示器 | 两帧间隔 | 错法的结果 |
|---|---|---|
| 60 赫兹 | 16.6 毫秒 | 刚好，你觉得对了 |
| 144 赫兹 | 6.9 毫秒 | 物理快一倍，角色起飞 |
| 掉帧 | 40 毫秒以上 | 逻辑被拉长，撞墙穿过去 |

原因只一句：增量时间归显示帧管，逻辑归固定步进管。拿错时钟去驱动逻辑，抖动只会原样进去。

## 两仓里真实的做法

`horizon` 有一条虚拟时钟，攒的是真实时间。`prisma-rev` 入口有`固定累加器`，攒的也是真实时间。两边不拿增量直推逻辑。下面是手写的最小示例：

```rust ref="prisma:crates/prism-app/src/app.rs#L1124-L1133"
// 入口测一次时间，再加进累加器；输入事件不决定模拟速度
let now = Instant::now(); // 瞬间：现在
let elapsed = last_frame.map(|p| now.saturating_duration_since(p)).unwrap_or(Duration::ZERO);
// 真实时间只负责往累加器加时长，累加器按固定步长产出 tick
```

```rust ref="horizon:crates/horizon-client/src/clock.rs#L47-L60"
// 残差攒时间，整格切走，剩下的是残差
let ticks = timer.advance_game_time(now_ms, |d| d.max(mspt));
// 完整切法见引用跳转：攒起来的时长切成整格 tick，余数留着
```

完整实现点引用块去 GitHub 看。教程代码行号从 1 开始，与真实文件行号无关。

## 双语对照

C++ 里同样的生产级毛病：

```cpp
// C++ —— 同样的毛病：两帧间隔驱动物理
#include <chrono>
auto now = std::chrono::steady_clock::now();
float dt = std::chrono::duration<float>(now - last).count();
physics::step(dt); // 144 赫兹下快一倍，掉帧穿墙
```

编译一次看它跑在两种刷新率下，速度差一倍：
```bash
g++ main.cpp -o engine && ./engine
```

C# 里也一样运行：

```csharp
// C# —— 同样的毛病：delta 直接驱动逻辑
var dt = Time.deltaTime; // 两帧间隔
physics.Step(dt); // 刷新率一变就飘
```

```bash
dotnet run
```

两边都把显示抖动带进了逻辑。解法都是先把步进固定，再让增量只负责往累加器加时长。`prisma-rev` 的步长是 16 毫秒多一点，`horizon` 用的是每秒 20 步。数不同，一回事。

## “死亡螺旋”先长在上限那

掉帧时如果一直追时间，越追越远。刹车那一步是上限。累加器攒多少、补多少、丢多少，下一课的“累加器”和后面的“每帧上限”里细讲。

:::warn{title="先这样记住"}
增量只往累加器里加时长。逻辑只认固定步长。哪边越界，画面和逻辑就对不上了。
:::

## 跟着看的结果

这一课验收只有一个：你能不看代码复述这句话。

> 增量归显示帧管，逻辑归固定步进管。拿错时钟去驱动逻辑，刷新率一变行为跟着变。

:::exercise{title="动手：亲手撞上毛病"}
打开任意一个演示，把刷新率从 60 改成 144，看移动速度涨没涨。再给一帧故意加 40 毫秒延迟，看角色穿墙没穿墙。记下三个时间点：60 赫兹、144 赫兹、掉帧。涨了，你就亲手撞上了这个毛病。改回来。
:::
