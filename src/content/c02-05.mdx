# 什么时候该拆包

拆包是决定负担，不是越多越好。拆太粗，编译慢、别人看不懂；拆太细，名字都记不住。这一课只学判断标准。

## 先把四仓的拆包摆上桌面

`Hazel` 的包地图在仓库根：`Hazel` 是引擎，`Sandbox` 是样例。查一个东西先看根目录有哪个包。

```bash
# Hazel 拆包：根上分三，一句职责说不清就拆
ls | head # 看引擎、样例、编辑器在哪个包
```

`MonoGame` 的包在框架仓根：`MonoGame.Framework` 是框架本体。查一个东西先看框架在哪个包。

```bash
# MonoGame 拆包：框架和测试分两
ls MonoGame.Framework | head # 看框架在哪个包
```

`Stride` 的包在 `sources/engine` 下：`Stride.Engine` 是引擎，`Stride.Graphics` 是图形。查一个东西先看引擎在哪个包。

```bash
# Stride 拆包：引擎、图形、游戏分三
ls sources/engine/Stride.Engine | head # 看引擎在哪个包
```

`prisma-rev` 的包在工作区清单里固定。`prism-app` 是应用层，`prism-engine` 是运行时。查一个东西先看清单在哪个包。

`horizon` 作需求方：`horizon-client` 是游戏，包固定，只借功能。

## 四仓对照表

| 写法 | 包在哪 | 按什么拆 | 拆了多付什么 | 适合谁 |
|---|---|---|---|---|
| `Hazel` 根上分三 | 仓库根 | 职责一句话 | 包散文件散 | 先看一眼 |
| `MonoGame` 程序集 | 框架仓根 | 框架/测试 | 版本一起升 | 传统生产图 |
| `Stride` 组件 | `sources/engine` 分三 | 引擎/图形/游戏 | 系统多 | 生态大，作架构对照 |
| `prisma-rev` 清单固定 | 工作区根 | 应用/引擎/渲染 | 名单明文 | 本教程主线 |
| `horizon` 清单固定 | 工作区根 | 游戏/世界/命令 | 名单明文 | 需求方 |

表上能看：`Hazel` 拆散，`MonoGame` 程序集旧，`Stride` 组件重，`prisma-rev` 清单固定。

## 本课定谁

不是选最简单，选生产级。单人引擎的拆包，我定 `prisma-rev` 的清单驱动：清单里声明依赖，`src` 里用包名调用。

理由有三条。

一是生产级。成员和依赖写死在清单里，环直接拦住。`Hazel` 那种全在根上，改个包名就断一片。

二是结构清楚。跨包只认公开名字，外层看不见没写公开的新名。查东西从应用层点名，名对得上。

三是可测试。层清楚了，测试也清楚。测试灌的都是包上层，不用把仓库全拖进来。

```rust
// 本课定案：拆包的样子
struct Crate {
    members: Vec<String>, // 成员名单：只写在哪
    deps: Vec<String>, // 依赖：写在各自清单里
}
```

## 三个信号出现时再拆

一个包里的文件开始出现下面三种信号时，拆分就划算。

第一，职责一句话说不清。C++ 里一个库同时管窗口和渲染，改窗口要重编渲染。C# 里一个项目同时对接渲染和物理，引用就拖进来一半。Rust 包也有同样的问题。

```rust
// 拆分前的样子：一句话说不清它管什么
// window 负责建窗口，也负责调渲染，还管存档

// 拆分后：窗口变成独立包
pub fn create_window(title: &str) -> Window { /* 只管窗口 */ }
```

第二，两个子模块的修改频率差很多。高频改动的地方独立成包，编译只重编它。C++ 里把不相关的源文件放一起，改一行要整库重编。C# 里把无关项目放进同一个大项目，改一个类要重编全部。拆开后改动只重编受影响的包。

第三，测试卡住了。测试必须拉起整个依赖链才能测一个小函数，说明边界没拆开。理想状态是小包可以只测它自己。

## 怎么拆

先按职责列一遍包的活，再一条条划界。线划在「改动原因不同」的地方。窗口改窗口的事，渲染改渲染的事，存档改存档的事。改动原因不一样，就别放同一个包。

对照写法：C++ 常用编译隔离（头文件只留声明），C# 常用项目引用（一个程序集引用另一个）。Rust 包就是把这个文件分组写进清单：`Cargo.toml` 里声明依赖哪个包，`src` 里用包名调用。拆完之后，旧包的公开名字不变，原来调用的地方大多不用改。

## 别提前拆

新项目先保持一个包。等职责边界稳定、测试变慢、编译变慢三件事出现再拆。过早拆会得到十几个互相牵着走的包，改一个功能要穿过好几个包。

完成标准：你能对自己的项目说出哪一句职责描述卡住了，以及它为什么还要等。

:::exercise{title="动手：给现在的项目划一次界"}
打开当前工作区，写下每个包的一句话职责。再找一个修改频繁的模块，看它能不能单独成包。不要现在就拆，只写理由，下一课用它定依赖方向。
:::
