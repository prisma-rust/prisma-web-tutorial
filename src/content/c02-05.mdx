# 什么时候该拆包

拆包是决定负担，不是越多越好。拆太粗，编译慢、别人看不懂；拆太细，名字都记不住。这一课只学判断标准。

## 三个信号出现时再拆

一个包里的文件开始出现下面三种信号时，拆分就划算。

第一，职责一句话说不清。C++ 里一个库同时管窗口和渲染，改窗口要重编渲染。C# 里一个项目同时对接渲染和物理，引用就拖进来一半。锈语包也有同样的问题。

```rust
// 拆分前的样子：一句话说不清它管什么
// window 负责建窗口，也负责调渲染，还管存档

// 拆分后：窗口变成独立包
pub fn create_window(title: &str) -> Window { /* 只管窗口 */ }
```

第二，两个子模块的修改频率差很多。高频改动的地方独立成包，编译只重编它。C++ 里把不相关的源文件放一起，改一行要整库重编。C# 里把无关项目放进同一个大项目，改一个类要重编全部。拆开后改动只重编受影响的包。

第三，测试卡住了。测试必须拉起整个依赖链才能测一个小函数，说明边界没拆开。理想状态是小包可以只测它自己。

## 怎么拆

先按职责列一遍包的活，再一条条划界。线划在「改动原因不同」的地方。窗口改窗口的事，渲染改渲染的事，存档改存档的事。改动原因不一样，就别放同一个包。

对照写法：C++ 常用编译隔离（头文件只留声明），C# 常用项目引用（一个程序集引用另一个）。锈语包就是把这个文件分组写进清单：`Cargo.toml` 里声明依赖哪个包，`src` 里用包名调用。拆完之后，旧包的公开名字不变，原来调用的地方大多不用改。

## 别提前拆

新项目先保持一个包。等职责边界稳定、测试变慢、编译变慢三件事出现再拆。过早拆会得到十几个互相牵着走的包，改一个功能要穿过好几个包。

完成标准：你能对自己的项目说出哪一句职责描述卡住了，以及它为什么还要等。

:::exercise{title="动手：给现在的项目划一次界"}
打开当前工作区，写下每个包的一句话职责。再找一个修改频繁的模块，看它能不能单独成包。不要现在就拆，只写理由，下一课用它定依赖方向。
:::
