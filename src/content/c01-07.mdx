# 你要交付的东西

这套课最后交付的不是一堆零件，而是一台能跑的引擎。它有窗口，能响应输入，能画出场景，能存档，能在断电前停下。

## 先定验收，再说交付

交付分四块，缺一块都不算交付完：可运行、可复现、可诊断、可交付。生产级交付单子先写四行，照着念。

> 可运行能跑起来，可复现能对上，可诊断能查到，可交付能到手。

## 四仓的交付分别长什么样

`Hazel` 的交付就是一个可运行的程序。`Sandbox` 编出来能跑，编辑器另算。没有可复现、诊断的单子，交付到手上是教学品。

```bash
# Hazel 交付：编一个能跑的程序
premake5 gmake && make -C build/Sandbox -j # 编一个
./Sandbox/bin/Debug/Sandbox # 跑一个
```

优点：编出来就是能跑，改改就是新程序。缺点：交付单只有一行，没复现没诊断，上线只靠跑通。

`MonoGame` 的交付就是一个能跑的游戏，打开就进。`Stride` 的交付就是带编辑器的整套工程。`prisma-rev` 的交付分两档：开发档能跑，发布档能签名。

`prisma-rev` 的根工作区成员是固定的，入口不在主工作区里。主工作区只列核心包，游戏二进制在 `projects/prisma` 的独立工作区里。`horizon` 是需求方：游戏也在主工作区里，入口是 `horizon-client` 的游戏。

```bash
# prisma-rev 的可运行：应用层窗口和渲染线程从这里起
cargo run -p prism-app 2>&1 | head # 看输出里该有的在不在
cargo run -p horizon-client 2>&1 | head # horizon 作需求方：游戏入口
```

## 四仓对照表

| 写法 | 可运行 | 可复现 | 可诊断 | 可交付 | 适合谁 |
|---|---|---|---|---|---|
| `Hazel` 可运行腾空 | 好，一个程序 | 差，没有种子 | 差，日志不分级 | 差，单档 | 先看一眼 |
| `MonoGame` 固定步长交付 | 好，打开就进 | 中，测试里写死 | 中，日志分级 | 中，单档 | 传统生产图 |
| `Stride` 组件系统交付 | 好，整套工程 | 中，快照测试 | 中，日志齐 | 中，工程重 | 生态大，作架构对照 |
| `prisma-rev` 固定累加器 | 好，双档 | 好，种子写死 | 好，渲染统计齐 | 好，双档可回滚 | 本教程主线 |
| `horizon` 需求对齐 | 好，游戏入口 | 好，种子写死 | 好，分级 | 好，签名检查 | 需求方 |

表上能看：`Hazel` 一行顶交付，`MonoGame` 打开就进，`Stride` 工程重，`prisma-rev` 双档且可回滚。`horizon` 只作功能对齐。

## 本课定谁

不是选最简单，选生产级。单人引擎的生产级交付，我定 `prisma-rev` 的双档：开发档能跑，发布档能签名。两档都写死在脚本里。

理由有三条。

一是可运行验收。`cargo run` 一行跑起来之后，看输出对不对。开发档对的，发布档也对的。

二是可复现验收。对着种子和快照，输出对得上。`Hazel` 那种没种子没快照的交付，崩溃没法重放。

三是结构清楚。单子记版本号，构建记产物。版本一变，单子就失效，要重验。

```rust
// 本课定案：交付的样子
struct Delivery {
    run: bool, // 可运行：能跑起来
    repro: bool, // 可复现：种子固定
    diag: bool, // 可诊断：日志分级
    ship: bool, // 可交付：双档签名
}
```

## 手写最小示例

```rust
// 交付四块：入口串起可运行，日志串起可诊断
fn main() {
    init_log(); // 可诊断：日志初始化
    if !reproducible() { log::warn!("种子未固定"); } // 可复现：查种子
    cargo::run(); // 可运行：跑起来
}
```

```bash
# 可运行：跑起来看输出
cargo run 2>&1 | head # 看输出里该有的在不在
```

```bash
# 可复现：种子固定，同输入同输出
cargo test 2>&1 | tail # 看测试全绿没
```

## 双语对照

C++ 的交付单子是安装程序，安装程序里带可运行的检查：

```cpp
// C++ —— 交付单子是安装程序，安装程序里带检查
// 1. 编出程序
// g++ main.cpp -o game
// 2. 安装程序检查可运行
./game --check
```

```bash
g++ main.cpp -o game && ./game --check 2>&1 | head
```

C# 的交付单子是自更新的清单，更新前能回滚：

```csharp
// C# —— 交付单子是清单，更新前能回滚
// dotnet publish -c Release
// ./game --check
```

```bash
dotnet publish -c Release 2>&1 | tail
```

Rust 的交付单子是打包后的双击运行加回滚开关。三种单子样子不同，验收一样。

## 不交付什么

交付不包括编辑器本身、包含测试用的二进制、带调试符号的开发档。这些是开发用的，发布版默认关。关掉的每样东西，都在发布脚本里有明文。

:::tip{title="交付是验收单"}
交付四项各有一张验收单：能跑的单子、能复现的单子、能诊断的单子、能交付的单子。单子没有，就当没交付。
:::

## 缺一块会发生什么

少可运行，读者接不到成品。少可复现，崩溃没法重放。少可诊断，故障只能猜。少可交付，成品到不了玩家手里。四块缺哪块，后面章节的着力点就不一样。

```text
[ ] 可运行：cargo run 跑起来
[ ] 可复现：种子固定，输出一样
[ ] 可诊断：日志分级，失败能报
[ ] 可交付：双档签名，能回滚
```

四行打勾，交付算成。`horizon` 里响应速度的边界写在配置里，默认关。关掉的东西回报率低，开了才算交付里有一项。`prisma-rev` 里可选能力默认关，暖起来才进交付。两边都把默认关写在明文里。

## 四仓再对照

`Hazel` 的 `Application::Run` 是可变步进，短但飘。`horizon` 的 `FixedStep::advance` 是虚拟时钟，牢但重。`prisma-rev` 的 `tick_sim` 是固定累加器，够用且可复现。本课往下走，只跟第三种。
